# 検証式の情報源・収集手法および検証倫理方針

## 1. 基本理念と一次検証者への倫理方針

艦これ（艦隊これくしょん）における各種戦闘・装備・ダメージ計算式は、運営公式から仕様や計算式が開示されることは原則としてありません。
現在コミュニティで広く知られている計算式のほぼすべては、**有志の一次検証者が莫大な出撃数、資材、時間を費やし、統計的推論と仮説検定を繰り返して導き出した貴重な知的成果物**です。

FUSOU プロジェクトにおいて検証式を収集・整理し、`fusou-datasets` による大規模データセットで追試・公開するにあたっては、以下の倫理方針を厳格に遵守します。

### 一次検証者への最大限の敬意

> [!IMPORTANT]
> **二次実装（既存のOSSシミュレータ等のコード）からの数式逆引き抽出は絶対に行いません。**  
> シミュレータから数式を抜き出すことは、血のにじむ検証を行った一次検証者のクレジットを不可視化し、シミュレータ開発者の努力にも敬意を欠く行為です。  
> 検証は、実際に検証を行った「一次検証者」を対象とし、一次情報源（Primary Sources）から直接収集・引用・追試します。

### 一次情報源のURLと完全なクレジットの明記
- 収集・公開するすべての検証式には、必ず**一次検証者が発表した元ページ（X/Twitterのポスト、個人ブログ記事、公開Googleスプレッドシート等）のURL**を直接掲載します。
- 検証者名（アカウント名 / ハンドル名）、発表日、および検証が行われた当時のゲーム環境・バージョンを明記します。
- 一次検証者が提示している前提条件や留保事項（「サンプル数N=XXのため暫定値」「特定装備構成のみで確認」等）を損なわず、そのまま掲載します。

### 著作権と適法な引用の遵守（著作権法第32条）
- FUSOU での検証式の引用および掲載は、科学的追試・再現性の検証・学術的比較を目的とし、[著作権と引用に関する運用方針](file:///docs/contents/policy/copyright_quotation_policy.md)に則り、引用の必然性と主従関係を厳格に保ちます。
- 原著作者から修正・削除の申し出があった場合は、速やかに対応する窓口を常時開設します。

## 2. 検証式の主な情報源（一次ソースの分類）

艦これの検証情報は、発表形式やデータの粒度によって以下の情報源に分類されます。

| 分類 | 主な媒体 | 役割と特徴 |
| :--- | :--- | :--- |
| **1. リアルタイム発表** | X (Twitter) / Togetter | 新仕様・新装備の最速一次発表、検証スレッド、相互査読 |
| **2. 検証レポート** | 検証者ブログ・note・個人サイト | 仮説設定、検証手法、回帰モデルの導出、考察記事 |
| **3. 生データ・集計** | 公開 Google スプレッドシート | 出撃生データ、分割表、信頼区間計算、特効倍率表 |
| **4. コミュニティ統合** | 攻略Wiki (wikiwiki.jp / 海外Wiki) | コミュニティによる知見の統合、集合的ナレッジ、議論ログ |

### A. X (Twitter) / Togetter
- **役割**: 新海域、新装備、運営アップデート直後の最速の一次発表の場。
- **特徴**:
  - 検証勢（検証クラスタ）のアカウントから、グラフや集計表のスクリーンショットとともにポストされる。
  - スレッド形式で追試結果や他検証者との議論・相互査読（ピアレビュー）が展開される。
  - 時間経過に伴い検索が極めて困難になるため、Togetter や min.togetter のまとめ、またはパーマリンクのアーカイブが重要。

### B. 検証者ブログ・個人サイト
- **役割**: 体系的な検証レポート、背景理論、統計モデルの導出解説。
- **特徴**:
  - なぜその数式モデル（線形、平方根、ロジスティック等）を適用したのかという仮説設定の背景が詳しく記述されている。
  - 代表的な検証サイトの例:
    - **黄金暗号**: 数理モデル、統計分析、検証式の理論的背景。
    - **誰得艦これ**: 改修効果、フィット補正、夜戦連撃・カットイン発動率などの詳細な実証。
    - **夢幻と黄昏の境界**: 基礎ダメージ計算式、キャップ前後の理論的整理。
    - **あきつ丸の検証ノート / 明石の改修工廠**: 装備改修値ごとの詳細な倍率検証。

### C. 公開 Google スプレッドシート
- **役割**: 検証の生ログ（Raw Data）、分割表、回帰分析の原典。
- **特徴**:
  - 出撃ログや戦闘結果（ダメージ値、命中/ミス）が1行ごとに記録された生データ。
  - 特効倍率表、対潜シナジー、支援艦隊のダメージ計算など、複雑な条件分岐を持つ検証で共有される。
  - 科学的追試を行う上で最も価値の高い一次データ源。

### D. 攻略Wiki（コミュニティナレッジ）
- **役割**: 広く合意が得られた検証結果の集約・一般化。
- **特徴**:
  - **艦これ攻略Wiki (wikiwiki.jp/kancolle)**: 「戦闘について」「命中と回避」「支援艦隊」「対空砲火」「改修工廠」などのページ。
  - コメント欄や「砂場（検証・作業ページ）」に検証者同士の議論ログが残されている。
  - **海外Wiki (en.kancollewiki.net / zh.kcwiki.org)**: 英語圏・中国語圏の検証知見が LaTeX 数式やテーブル形式で整理されている。

## 3. 一次情報の収集・構造化ワークフロー

散乱する検証式を体系化し、FUSOU 上で再検証可能な形で公開するための 4 段階の収集ワークフローです。

```
[Step 1: 一次ソースの発掘とパーマリンク特定]
    │ Xポスト、ブログ記事、スプレッドシートの一次URLを特定
    ▼
[Step 2: 数式メタデータスキーマへの構造化]
    │ 数式ID、LaTeX表現、検証者名、一次URL、前提条件を定義
    ▼
[Step 3: 生データの取得・保全]
    │ 公開スプレッドシートの生ログや分割表データをCSV/Parquet化
    ▼
[Step 4: fusou-datasets による科学的追試（Replication）]
    │ Train/Validation 分割による追試と検証スコア（Brier/KS）の算出
    ▼
[公開: FUSOU-WEB & ドキュメントでの透明な開示]
```

### Step 1: 一次ソースの発掘とパーマリンク特定
- Wikiの出典注釈、検証者のブログ記事、Xの検証ハッシュタグ（`#艦これ検証` 等）から、その数式が最初に提唱された**オリジナルの一次URL**を辿ります。
- まとめサイトや転載サイトではなく、**必ず実験・集計を行った本人の投稿・記事**を特定します。

### Step 2: 数式メタデータスキーマへの構造化
収集した数式は、以下の統一スキーマ（YAML）に落とし込み、メタデータを保全します。

```yaml
id: shelling_daytime_v1
name: 昼戦砲撃基本攻撃力・ダメージ計算式
category: shelling
status: verified # verified | community_consensus | hypothesis | disputed | deprecated

# 数式定義
formula:
  base_attack: "firepower + 5 + fit_bonus"
  capped_attack: "base_attack <= 360 ? base_attack : 360 + sqrt(base_attack - 360)"
  damage_min: "floor(capped_attack - armor * 1.3)"
  damage_max: "floor(capped_attack - armor * 0.7)"
  latex: "D \\in [\\lfloor A' - 1.3 \\times \\text{Armor} \\rfloor, \\; \\lfloor A' - 0.7 \\times \\text{Armor} \\rfloor]"

# 一次情報源（敬意とクレジットの完全明記）
sources:
  - type: blog_post
    title: "昼戦砲撃戦における攻撃力と装甲乱数の検証"
    author: "検証者名 / ハンドル名"
    url: "https://example-blog.jp/kancolle/shelling-analysis"
    published_at: "2018-05-10"
  - type: spreadsheet
    title: "昼戦ダメージ観測生ログ N=5000"
    author: "検証者名"
    url: "https://docs.google.com/spreadsheets/d/..."
  - type: tweet_thread
    author: "@researcher_kancolle"
    url: "https://x.com/..."
    published_at: "2021-03-01"

# 前提条件・適用範囲
conditions:
  combat_type: "day_shelling"
  target: "surface_ship"
  applicable_cap: 360
  notes: "装甲乱数は U(0.7, 1.3) の一様分布に従うと仮定"

# FUSOU による追試情報
verification:
  notebook: "packages/fusou-combat-research/examples/verify_shelling_damage.ipynb"
  dataset_query: "Tables.Battle.filter(phase='day_shelling')"
  sample_count: 10000
  hit_rate: "100.0%"
  last_verified_at: "2026-09-21T08:40:00Z"
```

### Step 3: 生データの取得・保全
- 公開されている Google スプレッドシートについては、CSV エクスポート形式（`/export?format=csv&gid={gid}`）を用いて生データを取得し、データ構造を保存します。
- 一次検証者が公開している分割表やパラメータ推定値を記録し、後から第三者が検証プロセスを追跡できるようにします。

### Step 4: `fusou-datasets` による科学的追試
- FUSOU データセットの 3 層分割（`train`: 70%, `validation`: 20%, `test`: 10%）を用いて、一次検証者が提唱した式を追試します。
- **過学習の防止**: パラメータの探索・適合には `train` のみを使用し、評価は完全未知の `validation` データセットに対して行います。
- **統計的検定**:
  - 確率モデル（命中率等）: Brier Score（平均二乗誤差）および較正曲線（Reliability Diagram）
  - ダメージモデル: 理論ダメージ区間 $[D_{\min}, D_{\max}]$ への的中率（Hit Rate $\ge 99\%$）
  - 乱数モデル: コルモゴロフ・スミルノフ検定（KS-test, $p > 0.05$）

## 4. 検証ステータス定義（信頼度の可視化）

公開する数式には、その検証の成熟度・合意度に応じた**検証ステータス**を付与し、利用者が信頼性を判断できるようにします。

| ステータス | 判定基準 | 説明 |
| :--- | :--- | :--- |
| **`verified`**<br>(FUSOU検証済み) | FUSOU の大規模データセットで統計的検定（Brier score < 0.25, KS検定 p > 0.05 等）に合格し、再現性が確認された式。 | 最も信頼性が高く、シミュレータや編成計算に安全に利用できる状態。 |
| **`community_consensus`**<br>(コミュニティ合意) | 検証者の間で長年支持され、広く合意形成されているが、FUSOU データセットでの網羅的追試が未完了の式。 | 有力な定説だが、データセットによる厳密な再検証待ち。 |
| **`hypothesis`**<br>(仮説・提案段階) | 個人ブログやX等で提唱されているが、サンプル数が少ない、または特定の条件下のみで報告されている式。 | 新装備・新仕様など、今後の追試が必要な段階。 |
| **`disputed`**<br>(諸説あり) | 複数の検証者間で異なる数式モデルや係数が対立している式（例: 対潜攻撃力のキャップ適用順、改修命中の平方根則 vs 線形則など）。 | 両方の数式・主張・一次ソースURLを併記し、FUSOU データでの比較検証対象とする。 |
| **`deprecated`**<br>(旧式・失効) | 運営アップデート（昼戦・夜戦キャップの引き上げ、新システム導入等）により過去のものとなった式。 | 歴史的経緯と変更前後の差分を記録するために保持。 |

## 5. まとめと今後の運用

1. **一次検証者ファースト**:
   数式を掲載する際は、必ず一次検証者の発表元URLとクレジットを最前面に表示し、検証者コミュニティの貢献を明示します。
2. **科学的追試の自動化**:
   各式に対して `verify_*.ipynb` のような自己完結型の検証ノートブックを作成し、CI パイプラインで定期実行して最新の適合度を公開します。
3. **異説・反例のオープンな受け入れ**:
   FUSOU データセットでの追試で不適合となった場合や、検証者間で見解が分かれている場合は、断定を避け、複数の説とそれぞれの一次ソースを併記してコミュニティの検証議論を後押しします。
