# TLSNotary P0-05 FUSOU-MITM Origin Transport Architecture v1

Status: architecture freeze only. No prover integration, Game Server traffic,
Presentation generation, replay, or production rollout is authorized by this
document.

```text
P0-04 = PASS
P0-05 = BLOCKED
IMPLEMENTATION = NO-GO
```

## 1. Decision

The selected target is **alpha.15 at the FUSOU-MITM origin boundary**:

- The FUSOU-MITM origin path embeds or delegates to the frozen alpha.15
  Prover-owned origin transport.
- That transport serializes the exact `require_info` request selected by
  FUSOU-MITM, including the binding, and writes it through the alpha.15
  `TlsConnection`.
- The alpha.15 Verifier owns the origin TCP socket and forwards bytes to the
  allowlisted Game Server.
- The browser-facing MITM session remains an upstream input boundary and is
  outside the cryptographic claim.

This is a target architecture, not an implementation claim. The current
repository starts an external WebView or browser through PAC and a MITM proxy,
then creates an independent Hyper/rustls origin client. It does not currently
show an alpha.15 `TlsConnection` integration at that origin boundary. Until
that transport boundary exists, no real FUSOU authenticated Presentation can
satisfy the frozen origin evidence contract.

A client-owned alpha.15 transport is also technically valid and would provide a
stronger browser/client provenance property, but it is not required for the
requested claim. The other architectures are evaluated below against the
origin-only P0-05 boundary.

## 2. Security objective

A qualifying Presentation must let the FUSOU verifier establish, from one
alpha.15 authenticated TLS session:

1. the allowlisted Game Server identity;
2. the complete disclosed sent and received transcript required by the frozen
   `require_info` evidence contract;
3. the exact HTTP request, including the binding header, and exact response
   bytes;
4. the transcript ranges and digests used by the FUSOU adapter; and
5. the alpha.15 Attestation and Notary context bound to those bytes.

The `api_member_id` authority is the authenticated `require_info` response
parsed by the verifier. A local capture, a client-supplied member ID, a copied
request, or an equivalent request generated by a proxy has no authority.

The target does not claim that TLSNotary alone proves an external browser or
Game Client originated the bytes. Browser intent, browser TLS, and browser-side
modification are outside the requested cryptographic claim. Natural-client
provenance remains a separate P0-04 operational evidence class.

## 3. Origin-request invariant

For P0-05, the authenticated `require_info` request must be the exact request
selected and sent once by the FUSOU-MITM origin path.
The following must all hold:

- the origin path selects the final endpoint, method, headers, body, and
  server-issued binding before serialization;
- the request is written once through the Prover-owned `TlsConnection`;
- the authenticated transcript contains the exact bytes sent by FUSOU-MITM;
- no capture artifact is copied into a later proof request; and
- a failed proof or delivery path never resends the already sent request.

An opaque binding value may be delivered to the origin path as a one-shot
control input. It must be present before origin serialization and must be
authenticated as part of the sent transcript. The browser does not need to see,
generate, or attest this value.

## 4. Byte ownership and trust

| Byte or object | Owner on the selected path | Who may modify it | Evidence meaning |
| --- | --- | --- | --- |
| Upstream plaintext request model | FUSOU-MITM origin path | The origin request builder before serialization | Unauthenticated input to the requested claim |
| Serialized HTTP request before origin TLS | Prover-owned origin transport | The same transport before the write latch | Candidate input to the authenticated sent transcript |
| FUSOU-MITM origin TLS ciphertext | alpha.15 Prover and its `ProxyTlsClient` | TLS implementation and protocol peers; no browser-facing MITM | Authenticated only as the origin TLS session owned by the Prover |
| Prover application transcript | alpha.15 Prover | No FUSOU capture or proxy component | Source for disclosed authenticated request and response ranges |
| Game Server response | Game Server, transported through Verifier-owned origin socket | Verifier forwards bytes; it does not establish server identity | Authenticated only after alpha.15 verification and disclosure checks |
| Exact-wire capture | FUSOU-PROXY capture subsystem | Capture writer may persist an observation | Useful observation and provenance artifact; never a cryptographic authority |
| Binding value | FUSOU Session/Challenge authority | Origin transport consumes it once | Must match the authenticated request and server-side authority record |

A byte being observed at the MITM plaintext boundary does not make it an
alpha.15 authenticated byte. Conversely, an alpha.15 authenticated byte does
not by itself prove that an unrelated external client originated it.

become A or B rather than the external-stream architecture described here.

## 6. Selected topology

```text
FUSOU-MITM origin request builder
        |
        | exact HTTP request, including binding, written once
        v
alpha.15 Prover-owned TlsConnection / ProxyTlsClient
        |
        | encrypted multiplexed alpha.15 Session stream
        v
alpha.15 Verifier and Notary-side service
        |
        | verifier-owned origin TCP socket; byte forwarding only
        v
allowlisted Game Server
```

The ordinary observation path remains separate:

```text
external WebView or browser
        -> PAC
        -> current FUSOU-PROXY MITM
        -> Hyper / hyper-rustls origin client
        -> Game Server
```

The second path may support ordinary gameplay, PAC routing, capture, and
non-P0-05 diagnostics. It must not be described as the source of the selected
Presentation, and it must not be bridged into the selected path by replaying or
reissuing captured bytes.

## 7. Trust boundaries

1. **Origin request boundary.** FUSOU-MITM is responsible for constructing or
  selecting the exact `require_info` request and applying the binding before
  origin serialization. An external browser behind the current MITM is an
  upstream input, not an attested party.
2. **Prover boundary.** The alpha.15 Prover owns the rustls client state,
   client-side TLS transcript, `TlsConnection`, and the secrets required for
   proving. It cannot substitute for the FUSOU Session/Challenge authority.
3. **Session boundary.** The encrypted multiplexed alpha.15 Session carries
   the protocol streams. It is not itself proof that an external client made
   the application bytes.
4. **Verifier origin boundary.** The Verifier opens the origin TCP connection
   and forwards bytes between that socket and the Prover stream. The origin
   socket must not be silently replaced by the existing Hyper TLS client.
5. **Game Server identity boundary.** The server certificate and authenticated
   TLS transcript are accepted only through the pinned alpha.15 verification
   path and the FUSOU strict adapter.
6. **FUSOU authority boundary.** Session issuance, binding freshness,
   Challenge matching, device/user association, and one-time consumption are
   separate authority checks. They are not inferred from the Presentation.
7. **Capture boundary.** `CaptureIo`, `RawCaptureHook`, and capture manifests
   observe or persist bytes. They cannot mint authenticated transcript ranges,
   server identity, Attestation IDs, or Notary signatures.

## 8. Prover ownership and alpha.15 compatibility

The Prover must instantiate the alpha.15 `ProxyTlsClient` and expose its
`TlsConnection` to the HTTP client that creates the authenticated request.
The Session driver must be continuously polled while the TLS exchange and
closing protocol make progress. The Verifier must run the matching proxy mode
against its origin socket.

The pinned alpha.15 source is:

```text
v0.1.0-alpha.15
47aee45b53e06648c1b2ad3689b367b8c923fdec
```

The inspected client profile has these constraints:

- TLS 1.2 only;
- `secp256r1` key exchange only;
- the two TLS 1.2 AES-128-GCM ECDHE suites supported by the pinned client;
- a configured root store and DNS server name/SNI;
- optional client authentication;
- session resumption disabled;
- no inspected ALPN configuration; and
- HTTP/1.1 as the demonstrated application transport.

These constraints are part of the integration gate. No broader support is
assumed from the current `hyper-rustls` path.

## 9. Origin request interaction

The selected implementation must make the authenticated origin path explicit:

1. FUSOU-MITM receives an opaque one-shot binding control value;
2. it selects the target `require_info` origin request;
3. it serializes the exact request, including the binding header, through the
  alpha.15 origin `TlsConnection`;
4. it accepts the corresponding response through that same connection; and
5. it closes or finalizes the proof session without resending the request.

The current FUSOU-PROXY source does not demonstrate this path. It creates a
Hyper/rustls origin client after MITM termination. That is evidence for the
current implementation gap, not an alpha.15 proof path.

## 10. Binding-header handling

The binding contract is:

- FUSOU Session/Challenge authority issues an opaque binding value;
- the value is delivered to the FUSOU-MITM origin path as one-shot control
  state;
- the origin path writes exactly one
  `X-Attestation-Binding: <binding_value>` header on the `require_info`
  request before origin TLS encryption;
- the value is not placed in the request body, logs, client event payloads, or
  unrelated requests;
- duplicate, missing, expired, or moved bindings fail closed for identity; and
- the server-side Result must match the authenticated header bytes to Session,
  Challenge, owner, freshness, and single-use state.

A proxy may transport an opaque control message and may apply it while building
the origin request. The existing `RawCaptureHook` and current Hyper/rustls
request path cannot satisfy this requirement because they are not connected to
an alpha.15 Prover-owned origin session.

This resolves the architecture question but leaves an implementation
question: the repository still needs a concrete Session-to-client transport
for the one-shot value. That transport is a prerequisite and is not silently
assumed to exist.

## 11. Current proxy role

`packages/FUSOU-PROXY/proxy-https` may remain responsible for:

- PAC serving and ordinary route selection;
- current MITM operation for ordinary supported traffic;
- exact-wire observation and private capture artifacts;
- resource or asset capture unrelated to P0-05; and
- diagnostics that do not claim alpha.15 authentication.

It must not:

- be called the alpha.15 Prover endpoint;
- convert `CaptureIo` or a capture manifest into a Presentation;
- inject the binding after origin serialization or call browser provenance part
  of the cryptographic claim;
- create a second request from captured bytes for proof; or
- leave the current `hyper-rustls` origin leg active underneath the selected
  alpha.15 proof path.

## 12. Game Server compatibility status

Status: **UNKNOWN**.

No authorized compatibility run against the real allowlisted Game Server was

pinned alpha.15 TLS profile, accept the required SNI and HTTP/1.1 behavior, and
return the origin `require_info` exchange without requiring an unsupported

A successful local fixture exchange proves protocol wiring only. It does not
prove allowlisted Game Server compatibility or production origin evidence.

## 13. Presentation lifecycle

The lifecycle is one request and one proof context:

1. The authenticated FUSOU authority issues a Session and opaque binding.
2. The Prover and Verifier establish the alpha.15 Session channel.
3. Both sides commit and accept the matching proxy-mode configuration.
4. The Prover connects with the server name and pinned client configuration.
5. FUSOU-MITM writes one origin `require_info` request through the returned
  `TlsConnection`.
6. The Verifier connects its origin socket and forwards ciphertext; the Game
   Server response returns through the same TLS session.
7. The client closes the application exchange; the Prover finishes transcript
   processing and server-tag checks.
8. The Prover sends the disclosure/prove request. The Verifier checks ranges,
   identity, transcript commitments, and protocol state.
9. The Notary signs the alpha.15 Attestation. The Prover retains the matching
   Secrets and constructs the Presentation.
10. The FUSOU adapter verifies the Presentation and accepts only the complete
    frozen `require_info` profile, exact binding, identity, ranges, and
    digests.
11. FUSOU authority code matches and consumes the Session/Challenge context;
    only then may the Result become an identity input.

The adapter package remains the boundary for strict FUSOU semantics. The
alpha.15 Presentation must not be treated as a generic JSON or capture
container.

## 14. No-resubmission invariant

The request path has a one-way send latch:

```text
BEFORE_APPLICATION_SEND
  -> SEND_COMMITTED
  -> RESPONSE_AVAILABLE
  -> PROOF_FINALIZED
```

Before `SEND_COMMITTED`, setup failure may disable the identity attempt without
sending a Game Server request. After `SEND_COMMITTED`:

- no retry, timeout retry, reconnect retry, or fallback request may resend the
  same `require_info` operation;
- a Presentation failure produces an unverified identity result;
- a binding failure cannot be repaired by moving the old binding to another
  request; and
  - a later origin `require_info` is a new attempt with a new authority context,
  not a replay of the old request.

This rule applies equally to the Prover, Verifier, proxy boundary, and runtime
Result delivery.

## 15. Implementation boundary

### 15.1 MUST IMPLEMENT BEFORE A REAL PRESENTATION

- Replace the current Hyper/rustls origin client with an alpha.15 Prover-owned
  origin transport and make the FUSOU-MITM request use its `TlsConnection`.
  The browser-facing path does not need to change for this claim.
- Add the matching Verifier/Notary service integration around the existing
  `packages/FUSOU-TLSN-VERIFIER` adapter boundary. The service must own the
  origin TCP socket and keep the alpha.15 Session driver alive.
- Define and test the Session-to-origin one-shot binding control path before
  request serialization.
- Implement the send latch and fail-closed no-resubmission behavior.
- Prove the pinned alpha.15 TLS profile is compatible with the allowlisted Game
  Server before attempting evidence collection.
- Produce a real FUSOU-MITM origin exchange with complete authenticated sent and
  received ranges, authenticated server identity, exact binding bytes, and
  strict `require_info` parsing.
- Complete the independent privacy, runtime, Session/Challenge matching, and
  provenance evidence required by the frozen contract.

### 15.2 REQUIRED ONLY FOR LATER RUNTIME AUTHORITY

These are not needed to demonstrate a local alpha.15 fixture Presentation,
but are required before accepting a Result as FUSOU identity authority:

- FUSOU-WEB Session issuance and binding freshness enforcement;
- Challenge and authenticated user/device matching;
- one-time Session/Challenge consumption and idempotent claim handling;
- Result delivery, signature verification, and server-derived identity mapping;
- persistence, retention, redaction, and operational privacy controls; and
- production observability for send-latch, verifier, binding, and rejection
  outcomes without logging secrets or member data.

### 15.3 NOT REQUIRED

The following are not valid prerequisites or substitutes for the selected
architecture:

- extending the current MITM capture hook into a passive alpha.15 Prover;
- replaying a captured request or response;
- generating a second equivalent Game Server request from a proxy;
- changing PAC rules while leaving the external browser TLS session unchanged;
- treating a local proxy-origin fixture as production authenticated evidence;
- changing the frozen alpha.15 revision to avoid the compatibility gate; or
- running real Game Server traffic before the local transport, authority, and
  privacy gates are reviewed.

## 16. Unresolved external evidence

The following remain open and keep P0-05 blocked:

1. **Origin integration:** the current FUSOU-PROXY source shows a Hyper/rustls
  origin client, not an alpha.15 `TlsConnection` or verifier forwarding path.
2. **Binding placement:** the concrete Session-to-origin control channel and
  its pre-serialization header placement do not yet exist in the inspected
   path.
3. **TLS compatibility:** real allowlisted Game Server negotiation with the
   alpha.15 TLS 1.2 profile is unknown.
4. **Verifier deployment:** the production Session, Verifier, and Notary
   boundaries are not wired into the current proxy runtime.
5. **Natural provenance:** P0-04 operational evidence is separate from the
  P0-05 origin cryptographic claim and does not authorize this runtime.
6. **Privacy and lifecycle evidence:** retention, disclosure review, and
   runtime Result delivery remain separate gates.
