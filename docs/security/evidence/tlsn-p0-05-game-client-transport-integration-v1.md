# TLSNotary P0-05 Game Client Transport Integration v1

Status: source inspection and architecture decision only. No real Game Server
was contacted, no new natural capture was performed, no historical capture was
replayed, and no request or Presentation was generated by this document.

```text
P0-04 = PASS
P0-05 = BLOCKED
IMPLEMENTATION = NO-GO
```

The existing alpha.15 Prover-owned transport skeleton remains classified as
`LOCAL_TRANSPORT_INTEGRATION`. It demonstrates local request serialization
through a Prover-owned `TlsConnection`; it does not demonstrate natural
provenance from the supported Game Client and does not change the gate status.

## 1. Decision summary

The current supported Game Client does not expose a FUSOU-owned HTTP/TLS
transport. FUSOU-App either creates a Tauri external WebView or opens a system
browser. The game page and its JavaScript execute in that browser engine, which
owns request serialization and the client-facing TLS connection. FUSOU-PROXY
then terminates that client-facing TLS session and creates a separate origin
TLS connection with its Hyper/rustls client.

Therefore:

- PAC routing does not make the alpha.15 Prover the TLS client.
- The current MITM path cannot satisfy the frozen natural-provenance contract.
- Copying the browser's plaintext request into the existing Prover transport
  would authenticate a FUSOU-reconstructed request, not the browser's TLS
  session or an unbroken browser-originated transcript.
- A qualifying implementation needs a supported-client integration point at
  or before request serialization. The smallest viable target is the frozen
  B+D architecture: a modified or explicitly FUSOU-owned client request path
  constructs the ordinary request, applies the one-shot binding, and writes
  once through the alpha.15 Prover `TlsConnection`; the alpha.15 Verifier owns
  and forwards the origin socket.
- A standalone Rust request builder remains a transport prototype unless the
  supported Game Client actually delegates its ordinary request flow to that
  builder before serialization.

## 2. Scope and evidence limits

This review uses repository source and the frozen security documents only. It
does not inspect the live game page, fetch the Game Server, perform a browser
capture, inspect a new request, or use a historical capture as input.

The repository does not contain the Game Client's remotely loaded application
JavaScript that initiates `POST /kcsapi/api_get_member/require_info`. It also
does not identify the ordinary gameplay action that first causes that request.
Consequently, the following facts cannot be established from repository
source alone:

- the exact external JavaScript module or function;
- whether that code uses `fetch`, `XMLHttpRequest`, or another browser API;
- the final browser-generated header set and body schema;
- whether the request follows redirects;
- which cookies or other browser-managed authentication state are included; or
- whether the real server requires browser-specific TLS negotiation behavior.

Those unknowns are integration blockers, not permission to substitute a
FUSOU-generated request or to label the local skeleton as natural evidence.

## 3. Actual request and TLS owners

### 3.1 FUSOU launch path

The current source establishes this sequence:

```text
launch_with_options
  -> wrap_proxy::serve_proxy
       -> proxy_https::proxy_server_https::serve_proxy
       -> proxy_https::pac_server::serve_pac_file
       -> edit_pac
       -> native_cmd::add_pac
  -> create_external_window
       -> Tauri WebviewUrl::External(configured game URL)
     or
       -> webbrowser::open_browser(configured game URL)
```

The relevant implementation surfaces are:

- [`launch_with_options`](../../../packages/FUSOU-APP/src-tauri/src/sequence/launch.rs)
  starts the proxy/PAC path before opening the game client.
- [`serve_proxy`](../../../packages/FUSOU-APP/src-tauri/src/wrap_proxy.rs)
  installs or validates the proxy CA, starts the HTTPS proxy and PAC server,
  edits the PAC target, and applies PAC configuration to the host.
- [`create_external_window`](../../../packages/FUSOU-APP/src-tauri/src/window/external.rs)
  loads the configured game URL into a Tauri WebView or opens it in the
  configured external browser.
- [`external_init_script.js`](../../../packages/FUSOU-APP/src-tauri/src/window/scripts/external_init_script.js)
  changes layout and keyboard behavior. It does not create or serialize game
  HTTP requests and contains no `fetch`, `XMLHttpRequest`, or `require_info`
  implementation.

### 3.2 Browser engine and process

For the embedded mode, the FUSOU-App dependency configuration identifies:

- Linux: `webkit2gtk`, used by the Tauri WebView runtime;
- Windows: `webview2-com`, used by WebView2; and
- external-browser mode: the system or configured browser opened by the
  `webbrowser` crate.

The exact external browser process and its internal network implementation are
configuration and host dependent. In all modes, the browser/WebView network
stack is the current Game Client TLS owner. FUSOU-App does not currently
provide a request interception API that replaces that stack with an alpha.15
`TlsConnection`.

### 3.3 PAC and current proxy path

The generated PAC file returns a local `PROXY` for the configured Kancolle
server host and `DIRECT` otherwise. The PAC server serves the file and
`edit_pac` injects the runtime proxy address and host match. PAC therefore
chooses where the browser connects; it does not select the TLS implementation
used inside the browser.

The current proxy implementation in
[`proxy_server_https.rs`](../../../packages/FUSOU-PROXY/proxy-https/src/proxy_server_https.rs)
establishes two distinct TLS boundaries:

```text
browser/WebView TLS
  -> generated or configured FUSOU CA
  -> hudsucker MITM termination
  -> Hyper request handler and optional capture hook
  -> Hyper hyper-rustls origin client
  -> Game Server
```

The code constructs an `RcgenAuthority`, an `HttpsConnectorBuilder`, and a
Hyper client, then supplies that client to `hudsucker::Proxy::builder()`.
`RawCaptureHook` observes the client-facing plaintext stream after MITM TLS
accept and before Hyper parsing. `LogHandler` collects and reconstructs HTTP
messages for logging. These are observation and proxy functions, not an
alpha.15 session attachment mechanism.

The exact current ownership is therefore:

| Boundary | Current owner | P0-05 consequence |
| --- | --- | --- |
| Game JavaScript request intent | External game page, not present in this repository | The initiating code is not currently controlled by FUSOU-App |
| HTTP serialization | WebKit/WebView2 or external browser network stack | Browser-generated bytes enter before FUSOU's MITM |
| Client-facing TLS | WebKit/WebView2 or external browser TLS stack | Not alpha.15 Prover-owned |
| MITM termination | FUSOU-PROXY/hudsucker | Creates a new plaintext/proxy boundary |
| Origin TLS | FUSOU-PROXY Hyper/hyper-rustls client | A separate TLS session, not the browser session |
| Current capture | `RawCaptureHook` and `CaptureIo` | Passive observation only; not cryptographic authority |

## 4. `require_info` call path

The repository contains the endpoint contract and parser/schema references,

The strongest source-grounded call path is therefore:

```text

  -> JavaScript/application code (not shipped in this repository)
  -> browser networking API (fetch/XHR/API is not established locally)
  -> WebKit/WebView2 or external-browser request serialization
  -> browser TLS
  -> PAC-selected FUSOU-PROXY MITM
  -> Hyper origin client
  -> POST /kcsapi/api_get_member/require_info
```

This review cannot truthfully name an external JavaScript function, choose
`fetch` versus XHR, or assert body, redirect, cookie, or authentication
behavior. The existing gate ledger explicitly records that the repository does
not identify the ordinary gameplay action that first causes `require_info`.
The exact request owner is the remote Game Client running in the browser
engine, but the exact application-level initiator remains outside the local
source boundary.

## 5. PAC is not Prover ownership

The proposed shortcut is:

```text
Game Client
  -> PAC
  -> FUSOU local endpoint
```

That can only result in Prover-owned TLS if the endpoint is a transparent byte
tunnel and the browser continues to own TLS, in which case it is not Prover
ownership. If the endpoint terminates browser TLS, the browser session ends at
the endpoint and any subsequent alpha.15 TLS connection is a new session. If
the endpoint asks the browser to send an HTTP request over it, the browser's
TLS implementation still owns the encrypted connection unless the browser
network stack itself has been replaced.

PAC has no control over the browser's TLS state machine, certificate
validation, cipher selection, transcript capture, or `TlsConnection` object.
It cannot transfer those responsibilities to alpha.15. The P0-05 path must
therefore bypass the current PAC/MITM route and integrate at the supported
client's request/TLS boundary.

## 6. Evaluated integration architectures

The classifications below distinguish natural request semantics from TLS
transport ownership. A request can have the same method, path, headers, and
body as a browser request while still being a reconstructed request if a
different component serializes and sends it.

### A. Game Client directly uses a FUSOU/Prover HTTP and TLS transport

**Result: viable only with a real client integration.** This preserves natural
provenance if the supported Game Client itself creates the ordinary request
object and invokes the Prover-owned transport before serialization. The
alpha.15 Prover then owns the TLS client and the exact sent bytes.

The current WebKit/WebView2 and external-browser paths do not expose this
integration in the repository. No claim can be made that they can directly
consume the alpha.15 `TlsConnection`.

### B. Game Client supports a custom browser/network backend

**Result: conditionally viable.** A custom backend preserves provenance only
if it is the actual backend used by the supported Game Client for the ordinary
`require_info` operation and receives the request model before serialization.
It must serialize once through the alpha.15 `TlsConnection`, including the
binding header.

A normal HTTP proxy, PAC endpoint, or backend that receives already serialized
browser bytes does not satisfy this condition. No such custom backend is
present in the current Tauri integration.

### C. Game Client delegates requests to FUSOU before serialization

**Result: viable target and the clearest B+D implementation point.** The
supported Game Client must be modified or extended so that its ordinary
request path delegates the request model, browser-managed state required by
the operation, and one-shot binding control to a FUSOU-owned transport before
the final bytes are serialized. FUSOU then writes those bytes once through
the Prover-owned `TlsConnection`.

This remains natural under the frozen definition only if the delegation is
part of the supported client's ordinary request path. An IPC call made after
the browser has produced serialized bytes, followed by a new FUSOU request,
is reconstruction and is not sufficient.

### D. PAC redirects the TCP connection

**Result: rejected for P0-05.** PAC can route the browser's socket to a local
endpoint. It cannot replace the browser's TLS client. A tunneling endpoint
leaves the browser TLS owner unchanged; a terminating endpoint creates the
MITM/new-origin split. Neither produces an alpha.15 Prover-owned TLS for the
browser's natural request.

### E. Current MITM preserves or bridges the original TLS transcript

**Result: rejected.** The current MITM terminates the client-facing TLS
session and creates an independent Hyper/hyper-rustls origin session. There is
no alpha.15 mechanism here that attaches to the browser session or turns the
two sessions into one authenticated transcript. A transcript bridge would
also violate the frozen no-replay/no-reconstruction rule and is not to be
built.

### F. Dedicated FUSOU request path inside the application

**Result: transport-feasible but not automatically natural.** A dedicated
FUSOU request path can use the existing local Prover-owned skeleton and can
prove local transport ownership. If it constructs `require_info` itself and
sends it without the supported Game Client delegating its ordinary operation,
the authenticated bytes are FUSOU-generated bytes. They are not natural Game
Client evidence.

This option becomes a qualifying B+D path only when the supported Game Client
is modified, embedded, or adapted so its ordinary request flow reaches this
path before serialization. The current skeleton has not established that
condition.

## 7. Which architectures preserve which claim?

| Architecture | TLSNotary authenticates | Natural Game Client provenance under the frozen definition | Status |
| --- | --- | --- | --- |
| A, direct client transport | The request sent by the integrated client transport | Yes, if the actual supported client constructs the request before the Prover write | Conditional viable |
| B, custom browser backend | The bytes emitted by the backend | Yes only if it is the ordinary supported-client backend before serialization | Conditional viable |
| C, pre-serialization client delegation | The bytes serialized by the delegated FUSOU transport | Yes, if delegation is part of the ordinary client request path | Selected B+D target |
| D, PAC routing | Browser TLS bytes or a second endpoint session | No transfer of TLS ownership; no Prover ownership | Rejected |
| E, current MITM | New proxy-origin TLS bytes | No; client and origin sessions are distinct | Rejected |
| F, standalone FUSOU request | FUSOU-generated request bytes | No, unless the supported client actually invokes it as its ordinary path | Prototype only |

The same plaintext bytes are not enough. The provenance decision depends on
which request owner creates the final serialized request and whether that
owner is the supported Game Client path, while TLSNotary depends on which TLS
client writes those bytes.

## 8. Binding header ownership

The frozen contract requires exactly one authenticated
`X-FUSOU-Attestation-Binding` header in the `require_info` request. The value
must be available before serialization and must be consumed once.

| Insertion point | Byte creator | TLS owner | Natural-provenance result |
| --- | --- | --- | --- |
| Game Client request layer | The supported Game Client or its integrated request adapter | Alpha.15 Prover-owned transport after integration | Compatible, if this is the ordinary request path and the header is applied before serialization |
| FUSOU-owned transport before serialization | FUSOU request transport, using a one-shot authority input | Alpha.15 Prover-owned transport | Compatible only when the supported Game Client delegates its ordinary request model to this transport before serialization; this is the frozen B+D target |
| Current MITM after TLS termination | FUSOU-PROXY | Browser TLS already ended; proxy creates separate origin TLS | Not compatible; it mutates/reconstructs an external serialized request and cannot establish the required provenance |

The binding is therefore not a generic proxy header. A proxy may deliver an
opaque control value to an integrated request owner, but it may not insert the
header into already serialized browser bytes on the P0-05 path. The binding
must be included in the bytes that the Prover-owned TLS session authenticates.

## 9. Application-controlled serialization and natural provenance

The frozen architecture document permits application-controlled serialization
with an important boundary: the request-owning client transport selects the
endpoint, method, body, and ordinary headers; the binding is available before
serialization; the request is written once through the Prover-owned
`TlsConnection`; and no external proxy rewrites serialized bytes.

That definition permits a FUSOU-owned transport only when it is the actual
request path of the supported client. It does not permit this substitution:

```text
external browser creates or sends request
  -> FUSOU observes plaintext
  -> FUSOU reconstructs equivalent request
  -> Prover sends reconstructed request
```

The reconstructed request may be byte-equal to an observation, but it has a
different serializer, a different TLS client, and potentially different
cookies, timing, redirects, connection state, and browser-managed headers.
The frozen contract does not define that as natural Game Client provenance.

Accordingly, the existing local `build_require_info_request(...)`-style
builder must remain a test/prototype helper. It must not silently become the
production source of truth unless the supported Game Client is changed to
delegate the ordinary request to it before serialization and that integration
is separately evidenced.

## 13. Remaining blockers

P0-05 remains blocked by all of the following unresolved prerequisites:

1. A supported Game Client integration point that lets the ordinary
   `require_info` request reach a FUSOU/Prover transport before final
   serialization.
2. Source or an approved integration contract for the external game request
   owner, including the exact initiation API, body, cookies/auth state,
   redirects, and required ordinary headers.
3. A one-shot binding delivery path from FUSOU authority to that request owner
   before serialization.
4. A production Prover/Verifier/Notary lifecycle with the Verifier-owned origin
   socket, continuous Session driver progress, and no-resubmission behavior.
5. Demonstrated compatibility between the pinned alpha.15 TLS 1.2 profile and
   the allowlisted Game Server. This remains an external, future gate and was
   not tested here.
6. A real natural exchange with authenticated complete sent and received
   ranges, authenticated server identity, exact binding bytes, and strict
   `require_info` parsing.
7. Runtime authority checks for Session/Challenge ownership, freshness,
   single-use consumption, Result delivery, and identity mapping.
8. Independent privacy and operational evidence for the production path.

The current MITM capture path, PAC changes, a copied plaintext request, a
byte-equal reconstructed request, or the local deterministic origin cannot
remove these blockers.
