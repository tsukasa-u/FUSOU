## 1. Decision summary

The current supported Game Client reaches FUSOU-PROXY through a browser or
WebView. The browser-facing TLS session terminates at the FUSOU MITM, which
then creates a separate origin TLS connection to the Game Server with its
Hyper/rustls client. The requested proof boundary is this second connection,
not the browser-facing session.

The browser may supply any request content to FUSOU-MITM, including content
that has been modified before the MITM receives it. Under the requested claim,
that is an input to the Game Server, whose application logic and authentication
are responsible for deciding whether to accept it. FUSOU does not need to
prove the browser's intent or browser-side TLS session.

Therefore:

- PAC and browser/WebView transport ownership are not part of the requested
  cryptographic claim.
- The current Hyper/rustls origin client is not an alpha.15 Prover transport,
  so the current origin exchange is not yet TLSNotary-authenticated.
- The target implementation must make alpha.15 own the FUSOU-MITM-to-Game-
  Server TLS session, or place the alpha.15 Prover at the exact origin-byte
  boundary before those bytes are sent.
- The proof must bind the exact request bytes sent by FUSOU-MITM to the exact
  authenticated response bytes returned by the Game Server. It need not bind
  those bytes to the browser's original intent.
- The existing local Rust request builder remains a transport prototype until
  it is connected to the production MITM origin path.

## 2. Scope and evidence limits

This review uses repository source and the frozen security documents only. It
does not inspect the live game page, fetch the Game Server, perform a browser
capture, inspect a new request, or use a historical capture as input.

The repository does not contain the Game Client's remotely loaded application
JavaScript that initiates `POST /kcsapi/api_get_member/require_info`. It also
does not identify the ordinary gameplay action that first causes that request.
Consequently, the following facts cannot be established from repository
source alone:

- the exact external JavaScript module or function;
- whether that code uses `fetch`, `XMLHttpRequest`, or another browser API;
- the final browser-generated header set and body schema;
- whether the request follows redirects;
- which cookies or other browser-managed authentication state are included; or
- whether the real server requires browser-specific TLS negotiation behavior.

These browser-side unknowns are outside the requested proof claim. The
remaining relevant unknown is the exact HTTP request that FUSOU-MITM hands to
the origin transport and the exact response bytes returned by the Game Server.

### 2.1 Audit AI correction report

The requested evidence scope is:

> Prove the Game Server response on the FUSOU-MITM-to-Game-Server origin
> exchange, bound to the exact request bytes sent by FUSOU-MITM.

The earlier analysis misunderstood this scope in three ways:

- It treated browser request intent and browser-facing TLS ownership as
  requirements for the proof.
- It treated a browser-originated request forwarded by FUSOU-MITM as an
  invalid reconstruction, even though the requested claim starts at the
  FUSOU-MITM origin boundary.
- It investigated WebView2 request interception and WebKitGTK URI schemes as
  possible ways to move TLS ownership out of the browser, although browser
  transport ownership is irrelevant to the requested claim.

The corrected interpretation is:

- The browser is an upstream input source and is not an attested party.
- The Game Server is responsible for accepting or rejecting the request it
  receives, including any browser-side modification.
- TLSNotary must authenticate the separate FUSOU-MITM-to-Game-Server session.
- The current blocker is production alpha.15 integration on that origin leg,
  not browser request delegation.

## 3. Actual request and TLS owners

### 3.1 FUSOU launch path

The current source establishes this sequence:

```text
launch_with_options
  -> wrap_proxy::serve_proxy
       -> proxy_https::proxy_server_https::serve_proxy
       -> proxy_https::pac_server::serve_pac_file
       -> edit_pac
       -> native_cmd::add_pac
  -> create_external_window
       -> Tauri WebviewUrl::External(configured game URL)
     or
       -> webbrowser::open_browser(configured game URL)
```

The relevant implementation surfaces are:

- [`launch_with_options`](../../../packages/FUSOU-APP/src-tauri/src/sequence/launch.rs)
  starts the proxy/PAC path before opening the game client.
- [`serve_proxy`](../../../packages/FUSOU-APP/src-tauri/src/wrap_proxy.rs)
  installs or validates the proxy CA, starts the HTTPS proxy and PAC server,
  edits the PAC target, and applies PAC configuration to the host.
- [`create_external_window`](../../../packages/FUSOU-APP/src-tauri/src/window/external.rs)
  loads the configured game URL into a Tauri WebView or opens it in the
  configured external browser.
- [`external_init_script.js`](../../../packages/FUSOU-APP/src-tauri/src/window/scripts/external_init_script.js)
  changes layout and keyboard behavior. It does not create or serialize game
  HTTP requests and contains no `fetch`, `XMLHttpRequest`, or `require_info`
  implementation.

### 3.2 Browser engine and process

For the embedded mode, the FUSOU-App dependency configuration identifies:

- Linux: `webkit2gtk`, used by the Tauri WebView runtime;
- Windows: `webview2-com`, used by WebView2; and
- external-browser mode: the system or configured browser opened by the
  `webbrowser` crate.

The exact external browser process and its internal network implementation are
configuration and host dependent. The browser/WebView network stack owns only
the client-facing leg, which is outside the requested proof boundary. FUSOU-App
does not currently make alpha.15 own the separate FUSOU-MITM-to-Game-Server
origin connection.

External-browser mode remains outside FUSOU's direct request-control boundary;
opening a configured browser does not provide a supported pre-serialization
delegation hook to FUSOU-App.

The previously investigated platform-specific APIs are not required for the
requested proof:

- WebView2 exposes `WebResourceRequested`. The host can receive a
  `ICoreWebView2WebResourceRequest`, edit its method, URI, headers, and body,
  and set an `ICoreWebView2WebResourceResponse`. Microsoft documents that the
  request object may not contain headers added later by the network stack. If
  the host does not set a response, WebView2 continues its own network request;
  if the host sets one, the host supplies the HTTP response. Neither branch
  gives FUSOU ownership of WebView2's connected socket or TLS state machine.
  The current Tauri code uses WebView2 for keyboard and DevTools operations
  only; it does not register `WebResourceRequested` or an alpha.15 transport
  adapter. This is not a P0-05 blocker under the corrected proof scope. See
  the official [WebView2 request API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2webresourcerequest?view=webview2-1.0.3537.50), [request event args](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2webresourcerequestedeventargs?view=webview2-1.0.3537.50), and [WebResourceRequested event](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2?view=webview2-1.0.3537.50#add_webresourcerequested).
- WebKitGTK exposes custom URI scheme registration and network proxy
  configuration. A custom scheme callback handles requests made with that
  scheme; it is not a replacement for the normal remote `https` transport.
  The current Linux code registers neither a custom scheme nor a custom
  network backend. See the official [WebKitGTK URI scheme API](https://webkitgtk.org/reference/webkit2gtk/stable/method.WebContext.register_uri_scheme.html).

Consequently, no Windows-only WebView2 adapter or Linux WebKitGTK transport
replacement is required for this proof claim. Future browser integration may
still be useful for other goals, but it is not the path needed to authenticate
the FUSOU-MITM origin exchange.

### 3.3 PAC and current proxy path

The generated PAC file returns a local `PROXY` for the configured Kancolle
server host and `DIRECT` otherwise. The PAC server serves the file and
`edit_pac` injects the runtime proxy address and host match. PAC therefore
chooses where the browser connects; it does not select the TLS implementation
used inside the browser.

The current proxy implementation in
[`proxy_server_https.rs`](../../../packages/FUSOU-PROXY/proxy-https/src/proxy_server_https.rs)
establishes two distinct TLS boundaries. The browser-facing boundary is only
the input path; the requested evidence boundary is the origin path:

```text
browser/WebView TLS
  -> generated or configured FUSOU CA
  -> hudsucker MITM termination
  -> Hyper request handler and optional capture hook
  -> Hyper hyper-rustls origin client
  -> Game Server
```

The target origin path is:

```text
FUSOU-MITM HTTP handler
  -> exact request bytes selected by FUSOU-MITM
  -> alpha.15 Prover-owned origin TLS
  -> Game Server
  <- authenticated response bytes
```

The code constructs an `RcgenAuthority`, an `HttpsConnectorBuilder`, and a
Hyper client, then supplies that client to `hudsucker::Proxy::builder()`.
`RawCaptureHook` observes the client-facing plaintext stream after MITM TLS
accept and before Hyper parsing. `LogHandler` collects and reconstructs HTTP
messages for logging. These are observation and proxy functions, not an
alpha.15 session attachment mechanism for the origin leg. The Hyper/rustls
origin client is the concrete implementation gap for the requested proof.

The exact current ownership is therefore:

| Boundary | Current owner | P0-05 consequence |
| --- | --- | --- |
| Game JavaScript request intent | External game page, not present in this repository | Upstream input only; outside the proof claim |
| HTTP request presented to FUSOU-MITM | Browser/WebView or external browser | FUSOU-MITM receives this input; browser authenticity is not claimed |
| Origin HTTP serialization | FUSOU-PROXY Hyper request handler/client | Must be captured at the exact byte boundary used by alpha.15 |
| Client-facing TLS | WebKit/WebView2 or external browser TLS stack | Outside the proof claim |
| MITM termination | FUSOU-PROXY/hudsucker | Creates a new plaintext/proxy boundary |
| Origin TLS | FUSOU-PROXY Hyper/hyper-rustls client | Current session is not alpha.15-authenticated |
| Required origin TLS | Alpha.15 Prover-owned `TlsConnection` | Authenticates the exact origin request/response transcript |
| Current capture | `RawCaptureHook` and `CaptureIo` | Passive observation only; not cryptographic authority |

### 3.4 Application-layer WebView hooks do not imply TLS ownership

The distinction is material for P0-05:

| Hook or mechanism | What it controls | What it does not control | P0-05 classification |
| --- | --- | --- | --- |
| WebView2 `WebResourceRequested` | An HTTP request object and, optionally, the response delivered to the page | Browser-added late headers, the browser socket, and browser TLS | Out of scope; not required for the origin proof |
| WebKitGTK custom URI scheme | Requests using the registered custom scheme | Normal remote `https` requests and their TLS | Not a current `require_info` transport hook |
| PAC | Socket routing decision | HTTP serialization and TLS implementation | Routing only |
| Hudsucker MITM | Client-TLS termination and proxy-origin handling | The original browser TLS transcript | Observation/proxy only |

An application-layer hook can become a qualifying delegation point only if the
supported Game Client's ordinary request is deliberately routed through it
before final serialization and the resulting response is returned without a
browser retry or second request. The hook's existence alone does not establish
that property.

## 4. `require_info` call path

The repository contains the endpoint contract and parser/schema references,
including [`kc-api-dto`'s `require_info` module](../../../packages/kc_api/crates/kc-api-dto/src/endpoints/api_get_member/require_info.rs),
the proxy's `/kcsapi` capture handling, and the frozen evidence documents. It
does not contain the remote Game Client JavaScript bundle or its source map.

The source-grounded path relevant to this proof is:

```text
remote Game Client input
  -> browser/WebView request
  -> browser-facing TLS
  -> FUSOU-MITM termination
  -> FUSOU-MITM-selected HTTP request
  -> current Hyper/rustls origin client
  -> POST /kcsapi/api_get_member/require_info
  -> Game Server response
```

The browser-facing steps are upstream context only. The requested evidence
starts at the FUSOU-MITM-selected HTTP request and ends at the authenticated
Game Server response. The future alpha.15 integration must replace or wrap
the current origin client at that boundary without changing which request the
MITM sends.

## 5. PAC is not origin Prover ownership

The proposed shortcut is:

```text
Game Client
  -> PAC
  -> FUSOU local endpoint
```

PAC only routes the browser-facing connection to FUSOU-MITM. It does not
choose the implementation of the separate origin connection. That origin
connection is currently created by Hyper/rustls and must be replaced or
integrated with an alpha.15 Prover-owned transport.

The intended path remains:

```text
browser/WebView
  -> PAC-selected FUSOU-MITM
  -> exact HTTP request selected by FUSOU-MITM
  -> alpha.15 Prover origin TLS
  -> Game Server
```

No browser TLS state, browser certificate validation, or browser transcript
needs to be transferred to alpha.15 for this claim.

## 6. Evaluated origin transport integrations

The relevant decision is which component creates and sends the origin request
that FUSOU-MITM presents to the Game Server. Browser provenance is not a
separate acceptance criterion for this evidence.

### A. Replace the current origin client with alpha.15

**Result: selected target.** Integrate the alpha.15 Prover-owned
`TlsConnection` into the FUSOU-MITM origin path in place of, or immediately
below, the current Hyper/rustls client. The integration must preserve the
exact request selected by FUSOU-MITM, authenticate the returned response, and
complete the Verifier/Notary lifecycle.

This is the smallest change that addresses the actual P0-05 blocker. It does
not require changing WebView2, WebKitGTK, PAC, or the browser-facing TLS leg.

### B. Alpha.15 adapter at the origin serialization boundary

**Result: conditionally viable.** If the existing Hyper handler can expose the
request bytes and response bytes at a stable boundary, an adapter may place
alpha.15 there. The adapter must prove that the bytes authenticated by
TLSNotary are exactly the bytes sent by FUSOU-MITM, including the binding
header and HTTP framing.

The adapter must not merely observe a Hyper/rustls exchange after the fact.
Passive capture cannot retroactively make the current origin TLS session a
Prover-owned session.

### C. Keep the current Hyper/rustls origin client

**Result: rejected for P0-05.** Hyper/rustls can continue to serve ordinary
proxy traffic, but it does not provide the alpha.15-authenticated origin
transcript required by this gate.

### D. Standalone FUSOU request path

**Result: transport-feasible but not sufficient by itself.** The existing
local request builder can demonstrate alpha.15 transport behavior against a
deterministic origin. It becomes relevant to production only when connected
to the FUSOU-MITM origin path and its exact request/response handling.

### E. Browser-side request delegation or TLS replacement

**Result: out of scope.** WebView2 hooks, WebKitGTK APIs, PAC behavior, and
browser TLS ownership do not determine whether the FUSOU-MITM origin
transcript is authenticated. They must not be used as P0-05 blockers.

## 8. Binding header ownership

The frozen contract requires exactly one authenticated
`X-FUSOU-Attestation-Binding` header in the `require_info` request. The value
must be available before serialization and must be consumed once.

| Insertion point | Byte creator | TLS owner | Origin-transcript result |
| --- | --- | --- | --- |
| FUSOU-MITM request handler | The exact request selected by FUSOU-MITM | Alpha.15 Prover-owned origin transport | Target; apply the header before origin serialization |
| Alpha.15 origin adapter | FUSOU-MITM request plus one-shot authority input | Alpha.15 Prover-owned origin transport | Compatible if the adapter proves exact request and response byte ranges |
| Current Hyper/rustls origin client | FUSOU-PROXY | Hyper/rustls | Not yet TLSNotary-authenticated |

The binding is therefore part of the FUSOU-MITM origin request contract. It
must be included in the exact bytes that the alpha.15 Prover-owned origin TLS
session authenticates and consumed exactly once. The browser does not need to
see, generate, or attest this header.

## 9. Origin serialization and transcript binding

The controlling boundary is the FUSOU-MITM origin request. The origin
transport must select or receive the final method, target, headers, body, and
binding before serialization, then write the request once through the
alpha.15 Prover-owned `TlsConnection`. The Verifier/Notary path must cover the
complete sent and received ranges and the authenticated Game Server identity.

The browser may have produced, modified, or retried its upstream request. None
of those facts change the proof claim. The Game Server decides whether the
request received from FUSOU-MITM is valid. FUSOU must not claim that the
browser intended the bytes or received the same response.

The existing local `build_require_info_request(...)`-style builder remains a
test/prototype helper until it is connected to the production FUSOU-MITM
origin path. A copied browser request is acceptable as upstream input, but
the authenticated request must be the exact request FUSOU-MITM actually sends.

## 13. Remaining blockers

P0-05 remains blocked by all of the following unresolved prerequisites:

1. Production integration of an alpha.15 Prover-owned transport into the
  FUSOU-MITM origin path, replacing or wrapping the current Hyper/rustls
  origin client.
2. A precise byte-boundary contract proving which request FUSOU-MITM sends to
  the Game Server and which response bytes it receives.
3. A one-shot binding delivery path that applies the value before origin
  serialization and consumes it exactly once.
4. A production Prover/Verifier/Notary lifecycle with the Verifier-owned origin
  socket, continuous Session driver progress, and no-resubmission behavior.
5. Demonstrated compatibility between the pinned alpha.15 TLS 1.2 profile and
  the allowlisted Game Server. This remains an external, future gate and was
  not tested here.
6. A real origin exchange with authenticated complete sent and received
  ranges, authenticated server identity, exact binding bytes, and strict
  `require_info` parsing.
7. Runtime authority checks for Session/Challenge ownership, freshness,
  single-use consumption, Result delivery, and identity mapping.
8. Independent privacy and operational evidence for the production path.

Browser-side behavior, PAC routing, the current MITM capture path, and the
local deterministic origin cannot remove these blockers because they do not
provide an alpha.15-authenticated origin transcript.
