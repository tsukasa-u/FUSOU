# TLSNotary Audit AI Current-State Report 2026-09-07

## 1. Purpose

The requested objective is:

> Route the `require_info` request that actually occurs during ordinary FUSOU-APP gameplay into Experimental TLSN, and establish the P0-05 evidence chain for that communication.

The operator must perform ordinary gameplay in FUSOU-APP. The agent must not access the Game Server through a standalone probe, generated request, replay, compatibility check, synthetic client, or direct API call. Any Game Server access used for evidence collection is permitted only as a consequence of the operator launching FUSOU-APP and playing normally.

This report is intended for an independent audit AI. It separates repository facts, local synthetic validation, natural-capture evidence, and missing production evidence. It does not claim that P0-05 is complete.

## 2. Hard Constraints

The following constraints are normative:

- Game Server access is allowed only through operator-controlled ordinary FUSOU-APP gameplay.
- No standalone `require_info` request may be generated by the agent or a test executable.
- No direct Game Server compatibility probe may be run.
- No request may be injected, replayed, retried, or captured traffic may be resent as a substitute for ordinary gameplay.
- The Production route must remain available and unchanged by default.
- Experimental TLSN must be opt-in and fail closed when its required trust and transport components are absent.
- `api_member_id` must be derived only from authenticated response bytes before it can be called `verified_member_id`.
- Natural capture is not equivalent to TLSNotary authentication and cannot by itself satisfy P0-05.

The agent has not connected to the Game Server. The local tests described below use in-memory or local synthetic TLS origins only.

## 3. Intended Evidence Flow

The desired future flow is:

```text
operator launches FUSOU-APP
  -> operator performs ordinary gameplay
  -> browser emits the actual require_info request
  -> FUSOU MITM observes that request
  -> trusted Session/Challenge authority supplies an authenticated binding
  -> a Prover-owned alpha.15 TLS connection sends the selected request exactly once
  -> the real Game Server returns the response over that Prover-owned connection
  -> Notary/Verifier processing authenticates the transcript and disclosure ranges
  -> strict parser derives api_member_id from authenticated response bytes
  -> signed FUSOU Result is delivered to the approved consumer
```

The current repository does not implement this complete flow.

## 4. Current Repository State

### 4.1 Implemented foundations

The following foundations exist in the worktree:

- Strict HTTP request and response parsing for the fixed `require_info` endpoint.
- Strict binding-header parsing and binding mismatch rejection.
- Alpha.15 Presentation decoding and verification plumbing.
- Authenticated transcript types that cannot be constructed from unauthenticated parser output.
- Actual serialized request validation before a Prover-owned transport write.
- One-shot request state that rejects a second send.
- Natural exact-wire capture and provenance metadata handling.
- A default-off `experimental_tlsn_enabled` configuration field.
- A MITM handler gate that identifies the first actual `POST /kcsapi/api_get_member/require_info` request.
- A handler-level executor interface that can receive the request selected by the MITM handler.
- Fail-closed behavior when the executor is unavailable or a repeated request is observed.
- A `testplay:verify` runner that starts FUSOU-APP for operator-controlled natural capture and restores the user configuration afterward.

### 4.2 Actual production wiring status

The critical production path is not connected:

1. `serve_proxy` constructs `ExperimentalRequireInfoRoute` with `forwarder: None`.
2. `proxy-https/Cargo.toml` has no dependency on `fusou-tlsn-verifier` or the pinned TLSN runtime.
3. `ExperimentalRequireInfoProbe` is explicitly documented as unused by FUSOU-PROXY and FUSOU-APP.
4. When Experimental mode is enabled, the first actual request is selected but returns `503` because no Prover-owned origin transport exists.
5. When Experimental mode is disabled, the request proceeds through the ordinary Hyper/rustls client.
6. No runtime code currently opens a Prover-owned alpha.15 connection for the browser-selected request.
7. No production Session/Challenge authority or server-issued binding injection is present.
8. No real Notary endpoint, Dedicated Verifier service, production signer, or Web delivery path is present.

Therefore, ordinary gameplay currently does **not** produce an Experimental TLSN request. Enabling the current flag only causes a fail-closed `503`; it does not create P0-05 evidence.

## 5. Meaning of `testplay:verify`

`pnpm --dir packages/FUSOU-APP testplay:verify -- <absolute-private-directory>` is a human-operated natural-capture runner. It:

- writes a temporary configuration override;
- enables exact-wire capture to an absolute directory outside the repository;
- disables API/resource persistence and application upload/sender paths for that session;
- explicitly sets `experimental_tlsn_enabled = false`;
- launches `pnpm tauri dev`;
- instructs the operator to use only ordinary gameplay;
- restores the original configuration after exit.

It is suitable for collecting P0-04 natural exact-wire evidence. It is not an Experimental TLSN runner and does not establish P0-05.

On Linux, the path must be an absolute POSIX path, for example:

```bash
capture_dir="$(mktemp -d /tmp/fusou-natural-capture.XXXXXX)"
pnpm --dir packages/FUSOU-APP testplay:verify -- "$capture_dir"
```

The runner does not contact the Game Server by itself. Any Game Server traffic during this command is caused by the operator's FUSOU-APP ordinary gameplay.

## 8. P0-05 Assessment

Current decision: `BLOCKED` / `NO-GO`.

P0-05 cannot become `PASS` until all of the following are available and independently auditable:

1. A real operator ordinary-play session in FUSOU-APP produces the selected request.
2. The selected request is routed to a Prover-owned TLS connection without a Production resend.
3. The Prover connection reaches the real allowlisted Game Server only as part of that operator session.
4. A trusted Session/Challenge authority issues and binds the request to the intended session.
5. A real or approved Notary produces an alpha.15 attestation/presentation for the exact transcript.
6. Sent and received ranges cover the required request, binding, response framing, and response bytes.
7. Transcript digests and certificate/server identity are authenticated and verified.
8. `api_member_id` is derived only from authenticated response bytes.
9. A Dedicated Verifier validates the Presentation and constructs the canonical Result.
10. Production signing, delivery, privacy, persistence, and retry behavior are reviewed.

The current code satisfies none of the runtime/Notary portions that are missing from this list. The current fail-closed `503` is a safety property, not evidence of successful Experimental routing.

## 10. Recommended Next Action

Do not ask the operator to run the current Experimental flag. It cannot produce evidence and will fail closed.

The next implementation slice should be an explicit, reviewable FUSOU-App Experimental session component that:

- is enabled only by a dedicated test configuration;
- receives the actual request from the MITM handler;
- obtains a binding from a trusted authority before origin send;
- owns the TLSN session and origin connection;
- sends the actual request exactly once;
- returns the authenticated origin response to the browser;
- persists a private evidence bundle only after privacy checks;
- does not use the ordinary Hyper client for the selected request;
- exposes explicit failure and rollback behavior.
